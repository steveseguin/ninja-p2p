Recovery validation

How interrupted and relayed transfers were tested, and what the runs showed.

View source Suggest an edit v0.2.4

Run from a built checkout with a supported Node WebRTC adapter:

bash
npm run build
node scripts/validate-swarm-live.mjs --impaired
node scripts/validate-swarm-live.mjs --relay
node scripts/validate-swarm-live.mjs --impaired --relay
node scripts/validate-swarm-live.mjs --impaired --large

Each run creates an isolated random room and temporary files, then disconnects both peers and removes its own fixture. It does not use a streaming channel. Do not rebuild dist while a validator is running.

--impaired drops the first manifest page once and the first attempt for every 17th chunk, and delays other binary replies by 20 or 80 ms. It transfers 512 KiB in 512 chunks, interrupts after at least 128 verified chunks, disconnects the receiver, constructs a fresh manager, and reconnects. Assertions require resume from disk, request timeout recovery, and an exact final SHA-256 match. Production timeouts are retained. Loss is injected at the application-message boundary over real WebRTC; it is not an OS packet-loss emulator or a claim about SCTP loss rates.

--relay uses the bridge's existing TURN-only option and requires SDK statistics to confirm the selected candidate pair is relayed. A missing relay or unavailable quality report fails the check rather than being reported as a relay success. --large retains the 2 MiB fixture when combined with --impaired, prints progress every ten seconds, and allows 240 seconds for completion after restart. It can also be combined with --relay. This changes only the validator's deadline; production request limits and retry timing remain unchanged. The normal fixture is 2 MiB in 2,048 chunks. SDK getPeerQuality supplies the candidate type; these runs used installed SDK 1.6.0 and @roamhq/wrtc 0.8.0 on Windows with Node 22.14.0.

Results from this follow-up#

  • Direct impaired/restart run passed on host/host: 31 chunks and one manifest page deliberately dropped; 137 verified chunks resumed from disk; all 512 chunks verified in the completed file.
  • TURN-only run passed on relay/relay: 2,048 binary chunks, eight manifest pages, and matching final file SHA-256.
  • Combined impaired/restart + TURN run passed on relay/relay: 31 chunks and one manifest page dropped, 128 chunks resumed, and all 512 chunks verified. Elapsed transfer time, including manifest retrieval and restart, was 39,685 ms.
  • An earlier 2 MiB impaired run exceeded its 90-second deadline after reconnect. An instrumented repeat completed on host/host in 115,120 ms, including manifest retrieval and restart: 121 chunks and one manifest page dropped, 131 chunks resumed, and all 2,048 chunks verified against the final SHA-256.
  • The repeatable --impaired --large --relay check also completed on verified relay/relay in 138,737 ms: 121 chunks and one manifest page dropped, 129 chunks resumed, and all 2,048 chunks verified against the final SHA-256.

Why the larger check needs longer#

The repeat kept making progress beyond the old deadline. The session permits four outstanding requests per peer. Once measured, a peer's request timeout has a three-second floor. In this fixture, 121 deliberately unanswered requests consume roughly 363 request-slot seconds, or about 91 seconds across four slots, before normal delivery overhead. Restart can abandon a few requests early, so this is an explanation of the scale, not an exact timing prediction.

The evidence supports an insufficient validator deadline rather than a stuck transfer. Keep the production timeout floor: lowering it just to satisfy this fixture could charge slow healthy peers with failures and duplicate their work. The smaller default fixture keeps routine recovery checks practical; --large keeps the original stress case reproducible. Neither promises a latency target.

These are bounded recovery checks, not throughput benchmarks. They do not model bandwidth saturation, long outages, TURN service failure, or arbitrary packet loss. Keep command handlers idempotent; these tests do not introduce message acknowledgement retries or automatic command re-execution.
